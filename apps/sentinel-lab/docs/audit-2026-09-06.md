# Sentinel Lab experiment lifecycle audit — 6 September 2026

## Incident and cause

Diagnostic `bc3250d7-32bd-4062-9605-6f7c87691b51` belongs to job `rd-5eba19350bb0-dea81e25` on production commit `ba5bac3a549014ff31a7121cc5f1cfbedee0afee`. Vercel logged `SANDBOX_BOOTSTRAP_FAILED` at 20:48:55 UTC: both launcher probes attempted to enter `/vercel/sandbox/eidos`, which did not exist. Allocation succeeded; the engine did not start. The exact physical checkout location was not exposed by that error.

The old helper derived a directory from the repository name beneath a hard-coded workspace. Its test repeated that assumption. The replacement executes a stdlib Python probe from the provider's actual working directory, accepts exactly one complete checkout at that directory or an immediate child, verifies Git HEAD and required tracked files, and records source hashes before detaching the launcher. Missing, changed, ambiguous, and wrong-commit source trees fail closed.

## Repairs

| Process | Confirmed fault | Resulting behavior |
| --- | --- | --- |
| Source/launcher startup | Guessed absolute repository directory | Actual checkout, commit, interpreter and launcher verified; downloadable source receipt |
| Active artifact retrieval | Unconditional `stop()` after downloading or failing to find a file | Active compute remains running |
| Monitoring | A temporary command-inspection error could mark the engine failed and stop it | Only confirmed missing/exited commands produce failure; provider outages return retryable lookup errors |
| Snapshot retrieval | Implicit SDK auto-resume and incomplete error cleanup | Explicit retrieval sessions; all subsequent operations pinned to that VM; cleanup even on read failure |
| Expiry | Active status from a stopped snapshot was changed only in the response | `EXPIRED` is persisted and remains stable across later reads |
| Runtime bootstrap | Existing Python executable skipped dependency installation and verification | Installation and CPU Torch verification run even after a partial prior setup |
| Early/child failure | Request parse failure escaped the bootstrap handler; a child could exit without a terminal receipt | A failure receipt is committed; valid engine failure details are preserved |
| Artifact integrity | Manifest included changing process logs and polling receipts | Only immutable outputs are hashed in the manifest |
| HTTP diagnostics | Unknown retrieval errors were returned as client error 400 | Server/provider failures return retryable 502/503 and redacted diagnostic IDs |
| Readiness | Configuration preflight presented as `READY TO LAUNCH` | `SETTINGS READY`; live checks occur after launch |

The artifact HTTP route already existed. Its error responses and response headers are hardened here; this release does not introduce that route.

The SDK contract was checked against installed `@vercel/sandbox` 3.2.1 and the [Vercel SDK reference](https://vercel.com/docs/sandbox/sdk-reference). In particular, Sandbox-level file/command calls can auto-resume; a Session pins operations to one VM. Retrieval explicitly uses public `Sandbox.get({ resume: true })` when a snapshot must be read.

## What the evidence means

The local real-data slice contained 600 benign evaluation rows and no positive examples. It produced 301 false alerts and 299 true negatives (50.17% false-positive rate). Recall and ROC AUC were correctly undefined. The generated fixtures also had high false-positive rates (standard 89.55%; mechanism study 92.05%). These are successful execution checks, not evidence of useful detection quality, production safety, or held-out generalization.

The known failing Vercel startup boundary is repaired and regression-tested. This workspace has no Vercel Sandbox identity or Lab operator credential, so a post-release allocation, snapshot retrieval and download through the live operator session remain unverified. Local execution does not establish that those provider operations succeed.

The current list-and-count capacity check is advisory across simultaneous dispatches. Strict distributed admission requires a shared queue/lock; this release does not qualify concurrent multi-instance execution. The larger dedicated-runner profile and external infrastructure are also outside this production-Sandbox repair.
